# FlowWeave 行情业务落地场景调研

## 1. 结论

FlowWeave 不应追求用一条固定流程覆盖完整研发全过程。最适合的平台定位是：

> 以受治理的 Agent、证据、人工决策和可审计动作，完成边界明确的业务闭环；长期、不确定的问题由持久 Case 协作，并按需启动多个短 FlowRun。

行情领域首批建议落地三类流程：

1. 开盘前、开盘中和收盘后的业务巡检闭环。
2. 告警分诊、证据汇聚和有限止血闭环。
3. 数据修复后的刷新、传播和多层复核闭环。

第二阶段扩展：

- 统一行情接入评审和上线门禁。
- 美股时令切换、新市场或新数据源上线门禁。
- 新股、退市、转板、代码复用、公司行动等证券生命周期治理。
- 数据质量评分规则试算、发布影响评估和供应商选择建议。
- 事故复盘、重复问题统计、SOP 与监控规则反哺。

不建议做：

- 用一个大型 DAG 覆盖需求、设计、开发、测试、发布和运营全过程。
- 让 Agent 自主执行全市场切源、大范围修数、数据库删除或生产配置发布。
- 让单个 Agent 的一次 Finish 回复直接成为业务结论。

## 2. FlowWeave 已具备的基础

FlowWeave 已经具备支撑上述场景的大部分控制面能力：

- Node Asset：复用提示词、模型、能力与输入输出契约。
- Flow Definition：组织节点、控制边、端口映射和 Gate。
- FlowRun/Snapshot：冻结本次环境、能力和配置，确保可追溯。
- Attempt/Artifact：保留每次执行和不可变证据版本。
- START/END Gate：在执行前和产出后实施确定性或 Agent 审查。
- WAITING_HUMAN：Agent 主动请求人工信息后，可在同一 Attempt 继续执行。
- 人工输入、人工输出、接受、拒绝、重试、风险接受和补救分支。
- 逐步运行：完成当前节点后不自动启动后继，等待人员补充配置并显式启动。
- 连续运行与 Schedule：适合固定频率巡检和日报、周报。
- 节点会话与 Agent Workspace：保留事件树、工具过程、附件和工作区。
- Runtime、环境和能力不可变版本：满足复现、隔离和审计要求。

平台当前的主要矛盾不是“不能多轮协作”，而是产品与提示词仍容易把节点定义成一次性答题：Agent 的 Finish 被视为节点最终输出，节点又承担事实收集、分析、决策与验收多个职责，导致一次回复过早收口。

## 3. 行情业务全景

当前行情应用版图可概括为：

```text
交易所/供应商
  -> receiver/proxy：连接、解码、标准化、校验、分发
  -> Kafka/Redis/DB
  -> mem：实时快照、盘口、状态的低延迟内存服务
  -> service：实时、历史、基础、财务、静态与聚合业务
  -> calculator/scheduler/Flink：指标、K线、资金流、统计、归档和刷新任务
  -> interface/push/open：HTTP、RPC、Socket、WebSocket 与网关推送
  -> APP/PC/BSS/量化/数据平台等消费方
```

跨链路业务还包括：

- 港股、美股、A股、马股、沙特、期权、期货、OTC 和数字货币等市场差异。
- 多供应商、双源切换和高可用。
- 交易日、交易时段、夏令时/冬令时、盘前盘中盘后夜盘。
- 新股、停复牌、退市、转板、代码复用和公司行动。
- 实时行情、盘口、逐笔、分时/K线、资金流、成交统计、基础与财务数据。
- 巡检、告警、修数、任务刷新、发布、接入、复盘和数据质量治理。

这些工作中，最适合编排的不是“写代码”本身，而是重复发生、输入输出可结构化、结果可独立验证、存在明确人工决策点的闭环。

## 4. 候选场景排序

| 优先级 | 场景 | 适合原因 | 推荐运行方式 |
| --- | --- | --- | --- |
| S1 | 行情业务巡检闭环 | 高频、规则明确、只读起步、易衡量 | Schedule + 连续运行 |
| S1 | 告警分诊与证据闭环 | 当前已有经验和日志能力，能显著降低 MTTA | Event Trigger + Case + FlowRun |
| S1 | 修数后的刷新与复核 | 现有 SOP 多、后置动作易遗漏、验证条件清楚 | 逐步运行 + 人工 Gate |
| A1 | 统一行情接入评审 | 需求/QPS/实时性/权限/监控有明确治理门槛 | Case + 多个短 FlowRun |
| A1 | 时令切换/上线门禁 | Checklist 成熟、时点固定、风险高且适合门禁 | Schedule + 逐步运行 |
| A1 | 证券生命周期治理 | 多系统、多阶段、需要审批和生效后复核 | Event Trigger + Case |
| A2 | 数据质量规则治理 | 已有五维评分、推荐、试算和影响预览 | FlowRun + Gate |
| A2 | 事故复盘到治理 | 历史台账丰富，适合持续生成 SOP/监控改进 | Schedule + Case |

## 5. 三个首批流程

### 5.1 开盘/收盘行情巡检

#### 触发

- 各市场开盘前、开盘后 5～15 分钟、收盘后。
- 特殊交易日、半日市、时令切换和新股首日附加触发。

#### 节点建议

```text
加载市场日历与本次巡检策略
  -> 收集 receiver/供应商连接证据
  -> 收集 Kafka、mem、interface、push 运行证据
  -> 抽样实时价/盘口/分时/K线/状态/统计
  -> 多点、多源、接口与客户端交叉验证
  -> 异常聚类与影响范围判断
  -> Gate：证据是否完整、是否满足异常定义
      -> PASS：生成巡检记录
      -> FAIL：创建异常 Case，进入告警分诊子流程
  -> 人工验收
```

#### 输出

- 每项检查的事实、来源、时间和结果。
- 异常项、影响市场/品种/链路和置信度。
- 未能取证的项目，不得用“正常”替代。
- 巡检记录和新建 Case 的关联 ID。

#### 指标

- 人工巡检耗时。
- 开盘后 5 分钟内异常发现率。
- 误报率、漏报率。
- 未取证却被判正常的次数。
- 重复异常转治理任务的比例。

### 5.2 告警分诊与有限止血

#### 触发

- 无行情、延迟、错价、状态异常、K线异常、推送异常、任务失败。
- 客户反馈或巡检异常。

#### 节点建议

```text
告警归并与影响范围识别
  -> 检索历史案例、SOP、近期变更和责任应用
  -> 并行取证：监控点/APP、供应商、receiver、Kafka、mem、push/interface
  -> 生成多个根因假设及支持/反对证据
  -> Gate：是否存在足够证据支持止血建议
      -> 否：WAITING_HUMAN，要求补充指定证据
      -> 是：输出止血选项、风险、影响范围和回滚条件
  -> 人工审批
  -> 调用版本化动作能力执行有限动作
  -> 独立验证：接口、客户端、监控三重恢复
  -> 未恢复则回滚/升级；恢复则进入复盘 Case
```

#### 自动动作边界

- 默认只读。
- 可自动建 Case、通知、拉取证据和生成建议。
- 单证券、限定缓存刷新或限定批次重跑可在预批准策略下开放。
- 全市场切源、Nacos 发布、重启、大范围回放、生产修数和数据库操作必须人工审批。

#### 指标

- MTTA、MTTR。
- 首次影响范围识别时间。
- 错误归因率。
- 建议采纳率。
- 动作后业务恢复率和回滚成功率。

### 5.3 数据修复后的刷新与复核

行情现有大量 SOP 都不是“改完一个 Redis 值即结束”，而是还要执行刷新任务、覆盖服务内存、重算衍生结果并让客户端复核。这是非常适合 FlowWeave 的流程。

#### 触发

- 已审批的股本、昨收、状态、股票定义、盘口、分红、拆合股或 K 线修复。

#### 节点建议

```text
确认修复单与授权范围
  -> 生成修复前证据快照
  -> 计算影响范围和后续刷新任务
  -> START Gate：对象、环境、范围、回滚是否明确
  -> 人工执行或调用已治理修复能力
  -> 执行对应 xxl-job/缓存/内存/聚合刷新
  -> 多层复核：DB/Redis/mem/interface/客户端/衍生数据
  -> END Gate：范围内恢复、范围外无变化
      -> PASS：人工验收并关闭
      -> FAIL：停止扩散，进入补救会话或回滚
```

#### 指标

- 修复后残留不一致率。
- 二次返工率。
- 修复到客户端可见的时间。
- 范围外非预期变更数。
- “任务成功但业务未恢复”的误关闭次数。

## 6. 第二阶段流程

### 6.1 统一行情接入治理

统一行情接入并不是直接给 SDK 或地址。建议用 Case 承载一个接入申请，并依次启动短流程：

1. 需求包完整性检查：业务场景、市场、字段、QPS、RT、准确性、峰值和容灾要求。
2. 接入方式建议：HTTP、mem-rpc、socket-push 或 gateway。
3. 数据权限和使用边界审批。
4. 容量与高可用设计评审。
5. 监控、预警、日志和责任人验收。
6. UAT 样本与验收报告。
7. 上线后的定向观察。

Agent 负责补全问题清单、生成方案候选和验证包；产品、开发、安全和业务方在 Gate 上作决策。

### 6.2 时令切换、新市场和新数据源上线门禁

美股时令切换、期权或新市场上线已有成熟 checklist。平台可冻结本次 checklist 版本，自动比对：

- 交易日历、时区和 cron。
- 香港/新加坡或主备源配置。
- receiver 连接与订阅数量。
- Kafka topic、Consumer Group 和 Lag。
- mem、push、HTTP、Socket、PC/APP 出口。
- K线、入库、状态、夜盘和统计任务。
- CPU、内存、延迟和热点/冷门样本。

FlowWeave 只负责门禁、证据和观察，不替代发布平台。

### 6.3 证券生命周期事件

从规则较清晰的少数事件起步：

- 新股上市与待上市转正常交易。
- 退市/到期的延迟清理。
- 主板转 OTC、换代码和代码复用。
- 分红、拆股、合股。

建议流程是事件归一化、实体匹配、多源冲突检测、影响分析、人工审批、定时执行、跨系统验证。涉及历史数据删除、DBA 冷备和大范围重算时必须人工 Gate。

### 6.4 数据质量评分治理

`hq-service-data-quality-score` 已具备完整性、一致性、历史稳定性、及时性、冲突率五维评分，并支持供应商推荐、配置试算和发布影响预览。FlowWeave 可编排：

```text
选择市场/业务对象/模块
  -> 读取当前规则与样本
  -> 只读试算 before/after
  -> 分析受影响字段、规则和重算范围
  -> 独立 Agent 审查误伤与数据偏差
  -> 人工审批发布
  -> 执行受控重算
  -> 观察评分、冲突率和告警变化
  -> 异常时回滚规则版本
```

### 6.5 事故复盘与经验回流

故障关闭后自动生成复盘草案，但不要让 Agent 自动认定责任。建议节点：

- 从告警、会话、动作、监控和人工记录重建时间线。
- 区分直接原因、根本原因和触发条件。
- 检索相似事故和重复根因。
- 生成监控、SOP、代码、配置治理改进项。
- 人工确认后更新案例库。
- 周/月度聚合高频问题，建议新的巡检项和流程资产。

## 7. 人机协作流程范式

### 7.1 节点不输出“最终答案”，而输出阶段包

每个 Agent 节点只承担一种职责，输出结构化阶段包：

```json
{
  "facts": [],
  "evidence_refs": [],
  "hypotheses": [],
  "unknowns": [],
  "recommended_next_actions": [],
  "human_decision_required": false,
  "completion_criteria": []
}
```

Finish 的语义应是“本阶段已交付”，而不是“问题已经解决”。

### 7.2 结论必须来自门禁，不来自同一个 Agent 自证

- 取证 Agent：只收集事实。
- 分析 Agent：提出多个假设。
- 审查 Gate：验证证据完整性、反例和规则。
- 人工决策：批准高风险动作或接受风险。
- 验证 Agent：动作后独立取证，不复用执行 Agent 的自我判断。

### 7.3 充分使用现有 WAITING_HUMAN 与会话续接

当证据不足时，Agent 不应猜测，而应输出具体缺口并进入 WAITING_HUMAN。例如：

- 缺少另一监控点数据。
- 无法确认当前是否交易时段。
- 缺少目标环境或证券代码。
- 供应商与客户端结果冲突。
- 生产动作的授权范围不明确。

人工补充后在同一 Attempt 和会话继续，而不是重新创建一个脱离历史的新任务。

### 7.4 使用逐步运行处理不可预估路径

逐步模式适合告警调查、接入治理和修数：

- 当前节点完成后，只准备后继工作项，不自动启动。
- 人可根据阶段产物修改后继节点配置、输入、模型和能力。
- 已完成节点、会话、证据和 Gate 始终可回看。
- 重复出现的稳定路径再提炼为连续运行模板。

### 7.5 Case 与 Workflow 分离

建议新增持久 Case 产品模型：

```text
Case
  - 类型：Incident / DataQuality / Integration / Change / Lifecycle
  - 状态、严重度、责任人、SLA
  - 证据、决策、时间线、风险接受
  - 关联多个 FlowRun、会话、外部工单和变更
```

Case 可以持续数天或数周；FlowRun 在其中完成取证、修复、验证或报告等短任务。不要用一个永不结束的 FlowRun 模拟 Case。

### 7.6 证据成为一等对象

Artifact 除内容外，建议增加或规范：

- 来源系统、采集方式和查询条件。
- 事件时间、采集时间、新鲜度和有效期。
- 市场、环境、应用、证券和链路范围。
- 校验和、版本和脱敏状态。
- 支持或反对哪条假设。
- 被哪个 Gate、动作和人工决策引用。

### 7.7 动作能力必须治理

每个生产动作能力声明：

- 风险级别 R0 只读、R1 协同、R2 有限可逆、R3 高风险。
- 最大影响范围和目标资源类型。
- 硬前置条件、审批角色、幂等键和速率限制。
- 动作后验证、超时、补偿和回滚方式。
- 允许使用的环境和有效期。

Agent 可以建议动作，但不能用自然语言绕过确定性策略。

## 8. 90 天落地路线

### 第 1～3 周：只读巡检 MVP

范围：美股开盘巡检，覆盖全美、纳斯达克、期权和 OTC 的少量关键指标与样本。

建设内容：

- 固化巡检输入输出 schema。
- 接入市场日历、监控、日志、关键接口和 APP/PC 抽样证据。
- 建立 Schedule 和异常 Case 草案。
- 影子运行，与人工巡检并行比较。

验收：

- 连续两个交易周稳定运行。
- 证据可回溯率 100%。
- 不执行生产写操作。
- 人工巡检耗时明显下降，误报和漏报可统计。

### 第 4～7 周：告警分诊 MVP

范围：先覆盖“无行情”和“延迟”两类告警。

建设内容：

- 告警关联、历史案例检索和 receiver→Kafka→mem→push/interface 分层取证。
- 强制输出多个假设、反证和未知项。
- WAITING_HUMAN 补证据。
- 自动建 Case、通知和升级，不执行生产变更。

验收：

- MTTA 降低。
- 分诊报告被值班人员采纳。
- 不因 Agent 单一结论关闭事故。

### 第 8～10 周：修复后复核 MVP

范围：选择一个高频、低爆炸半径场景，例如单证券昨收/状态修复后的任务刷新和多层验证。

建设内容：

- 修复前快照、审批 Gate、刷新任务、接口/客户端/监控三重验证。
- 执行动作先由人工完成，FlowWeave 负责确认与验证。
- 稳定后再接入一个版本化、限定范围的 R2 动作能力。

验收：

- 不再遗漏刷新任务。
- “任务成功但业务未恢复”可被拦截。
- 范围外无非预期变化。

### 第 11～12 周：复盘和模板沉淀

- 汇总前三个 MVP 的运行数据。
- 把高频稳定路径升级为连续模板。
- 把非稳定路径保留为 Case + 逐步运行。
- 选择第二阶段场景：统一行情接入或时令切换门禁。

## 9. 平台产品改进优先级

### P0

1. **Case 模型**：长期问题关联多个 FlowRun，而非大 DAG。
2. **阶段性交付语义**：节点明确区分 `STAGE_COMPLETE` 与业务 `RESOLVED`。
3. **证据包与结论引用**：Gate 和人工审批能看到被冻结的证据快照。
4. **动作注册表与风险策略**：限制 Agent 可执行动作的范围与审批。

### P1

1. 动态计划：基于当前阶段产物选择后续子流程，但必须人工确认或受策略约束。
2. 四眼审批、职责分离、审批超时和转派。
3. 影子运行、历史回放和流程评测集。
4. 运行指标：人工介入次数、证据完整率、结论推翻率、动作成功率和业务恢复率。
5. 将会话中稳定经验一键提炼为 Skill、Gate 或流程模板候选，经评审后发布新版本。

### P2

1. 跨 Case 的相似问题检索和重复根因聚类。
2. 供应商 SLA 取证与争议 Case。
3. 流程版本效果对比和自动化授权逐级提升。

## 10. 最终判断

FlowWeave 的优势不应是让 Agent 一次性完成一切，而是把 Agent 的不确定推理放入确定性的治理框架：

- 事实有来源。
- 结论有反证。
- 缺口会等待人补充。
- 高风险动作有人批准。
- 执行和验证相互独立。
- 失败可以停止、回滚和继续协作。
- 每次处理都沉淀为可复用、可版本化的组织经验。

这比“完整研发流程自动化”更现实，也更接近 FlowWeave 最初要承载 Agent、技能和个人经验的目标。
