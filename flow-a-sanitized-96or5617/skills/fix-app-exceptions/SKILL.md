# Fix App Exceptions

以本地 `TASK.md` 驱动修复。飞书文档仅是阶段一/二证据输入，不承载修复过程；禁止写入父文档或指纹文档，不新增/维护第八章。

## Required inputs

需要异常标题级清单及对应阶段一/二证据链接，并由用户明确提供代码工作空间。必须从异常收集输入确定一个“异常收集应用”和开始/结束日期；修复账本固定为当前 AI Playbook 仓库 `tmp/{异常收集应用}-exception-fix-{MMDD}-{MMDD}/TASK.md`。日期只取窗口两端的月日，补零为 `MMDD-MMDD`，不得带年份、小时或分钟。用户提供的代码工作空间只用于放置 Git 仓库，禁止把 `TASK.md` 写入其中。未获得代码工作空间前，也可初始化 tmp 账本并询问路径，但不分析或同步代码。

读取修复工作区、代码工作空间和目标仓库适用的 `AGENTS.md`。代码来源统一使用 `$find-and-pull-hq-git`：先搜索候选并确认，新仓库 clone，已有仓库只 `fetch --prune origin`。

## Core gates

1. 在当前仓库 `tmp/{异常收集应用}-exception-fix-{MMDD}-{MMDD}/TASK.md` 创建或续办账本，不覆盖历史；代码工作空间与修复工作区必须分离。
2. 新建 `TASK.md` 时必须在激活首项前扫描历史账本：历史已跳过同指纹排除；历史已完成同指纹保留并标记待复核，轮到时先询问本次是否跳过。续办已有账本不追溯改写队列。一次只允许一个非终态活动项；批量跳过是标题级元数据操作的唯一例外。
3. 当前项先询问“处理或跳过”；用户选择处理前禁止读取详细正文、日志或代码。
4. 选择处理后完整读取窗口父文档和当前指纹 1–7 章，重建原始异常、reqId/access、上下游、SkyWalking、表面/二次异常的因果链，并标注证据等级。忽略旧文档中可能残留的第八章。
5. 代码准备阶段只创建本地无 upstream 任务分支，不得为分析预建批次基准。任务分支从同仓已存在且确认属于本批次的基准 HEAD 创建，否则从最新远端默认 commit 创建；完成前禁止读业务代码。
6. 分析完成后先建立“原可观察结果基线”和调用方矩阵，再比较候选修复层。优先级固定为：消费者可观察结果保真 > 修改范围最小 > 实现简洁；不得把“改动行数最少”当成首要标准。
7. 提交结果保真方案并等待明确确认；确认前禁止修改任何代码、测试、配置、依赖或生成文件。范围扩大、新增修改仓库，或任何消费者可观察结果变化时，必须退回方案确认。
8. 验证通过后给出 `fix: xxxxx [HST_AI_Tag: AI_Generated]`，等待用户选择“提交并归并”或“暂不提交”。确认前禁止 add/commit/merge。
9. 每问题每实际修改仓库一个 commit。用户确认提交归并且 commit 成功后，才按需创建本地批次基准，并仅用 `git merge --ff-only` 归并。归并阻塞只能由用户处理。
10. 任务分支永不 push。分析后无实际改动的任务分支，以及成功归并并校验后的任务分支，必须当项安全删除；批次末只对真正包含本批次修复 commit 的基准询问 push。
11. 所有修复选择、证据、方案、验证、commit、归并和 push 只写 `TASK.md`；不写飞书。

## TASK.md source of truth

使用 `references/task-template.md`。每次状态、确认、结论和验证变化后立即更新。若上位规则指定其他权威文件，保持同步；不一致时停止。

### Main statuses

- `未开始`：未轮到，禁止读取正文或代码。
- `待处理`：当前项等待处理/跳过选择。
- `处理中`：正在代码准备、分析、方案确认、修改验证或提交归并。
- `阻塞`：缺少证据、确认、仓库、权限或用户归并处理；不是终态。
- `已完成`：代码/无代码结论、验证和提交归并闭环均满足。
- `已跳过`：用户在预读正文/代码前明确跳过。

执行阶段：`代码准备 → 分析 → 方案确认 → 修改验证 → 提交归并`。

子状态：

- 代码准备：`不适用/待工作空间/待仓库确认/同步中/分支准备中/已完成/阻塞`
- 提交归并：`不适用/待选择/提交中/归并中/已归并/已覆盖/暂不提交/阻塞`
- 任务分支清理：`不适用/待判断/待清理/已删除/保留-阻塞`

`已覆盖` 必须记录覆盖任务/commit、祖先关系或差异及定向验证。`暂不提交`、`阻塞` 或任何 `保留-阻塞` 不能完成。

## Efficient batch skip

用户可以一次指定一组不处理项，例如：

- 明确 ID：`跳过 F008、F009、F011`；
- 标题/错误特征：`所有 Read timed out 都跳过`；
- 可审计条件：应用、endpoint、logger 或 root msg 的明确组合。

规则：

1. 只用 `TASK.md` 队列表的 ID、应用/仓库、标题和状态匹配；endpoint、logger、root msg 仅在已进入标题或应用列时才可作为条件，禁止为匹配补读子文档正文、日志或代码。多个条件按 AND 组合，文本匹配忽略大小写。
2. 条件有歧义时先展示命中 ID/标题，询问一次；条件明确时用户原始消息就是整批授权。
3. 默认只修改 `未开始/待处理` 项；不改变 `处理中/阻塞/已完成/已跳过`。若用户要放弃正在处理项，必须单独明确确认。
4. 一次原子更新全部命中项为 `已跳过`，记录批次 ID、原始确认文本、时间、匹配条件、命中/排除 ID 和“未读取正文/代码”。不要逐项询问，不创建每项冗长记录。
5. 保持原顺序，将首个未终态且未跳过项设为唯一 `待处理`；其他保持 `未开始`。
6. 优先使用 `scripts/batch_skip_task.py`：先 `--dry-run` 审核命中、排除和下一项，再去掉 `--dry-run` 原子应用。脚本应用前必须校验 ID、状态及唯一活动项；失败时不得部分写入。
7. 批量跳过只更新本地 `TASK.md`，不访问或修改飞书。

## Initialize

1. 用异常收集应用和窗口生成 `tmp/{异常收集应用}-exception-fix-{MMDD}-{MMDD}/`；同批次目录已有 `TASK.md` 时续办，禁止覆盖。不得在用户代码工作空间创建账本。
2. 在 `TASK.md` 固化批次身份：异常收集应用、原始时间窗口、规范化日期 `MMDD-MMDD`，以及唯一标准基准名 `feature/exception-fix-baseline-{异常收集应用}-{MMDD}-{MMDD}`。异常收集应用来自本批次阶段一/二输入，禁止改用当前修复仓库名、provider 名或调用链上的其他应用名；所有实际修改仓库使用完全相同的基准分支名。
3. 读取输入清单的标题级信息和完整指纹键元数据（应用、logger、endpoint/任务、root msg、首业务栈），创建仅含 `待处理/未开始` 的候选队列表；不读详细正文，不创建 Item record。
4. 执行历史终态门禁：至少扫描当前仓库 `tmp/**/TASK.md`，并兼容用户明确提供的旧账本根目录；只读取任务队列和批量跳过审计。优先使用 `$collect-app-exception-logs/scripts/filter_historical_skips.py`，先 `--dry-run` 再原子应用。
5. 匹配优先级为完整指纹键；旧账本字段不足时回退到 `应用 + 规范化异常标题`。历史 `已完成` 还可使用保守的标题相似候选（同应用、同 endpoint/标题主体、错误特征词重叠且达到相似度阈值），但只用于询问，禁止自动排除。历史明确批量标题规则对同应用继续生效。跨应用不继承。
6. 历史 `已跳过` 命中项从新队列物理移除，保留“历史跳过排除审计”；不计为本批次 `已跳过`。历史 `已完成` 命中项保留入队，保留“历史已处理匹配审计”。同一指纹两者均命中时，以已完成复现审查优先，保留并询问。
7. 对标题回退/批量规则的歧义命中先展示候选并确认。用户明确要求重新处理历史跳过项时才用 `--keep-current-id + --override-reason` 重新纳入。
8. 必须向用户逐项列出两类结果：当前 ID、标题、历史 `TASK.md`、历史 ID/规则、匹配级别和依据；汇报原始数/跳过排除数/已完成待复核数/实际入队数。0 命中也报告。
9. 审计完成后把剩余首项设为唯一 `待处理`，其余 `未开始`。若全被排除，报告无待修复项并结束初始化。
10. 记录用户代码工作空间；仅检查该目录已有仓库的 `git status --short`。
11. 若当前项出现在“历史已处理匹配审计”，先展示历史来源并询问：`该异常历史已处理，本窗口再次出现，是否跳过？` 选择跳过则记本批次 `已跳过`；选择不跳过/重新处理才进入正常处理流程。否则询问普通“处理或跳过”。任何选择前禁止读取正文或代码。

历史排除只改变修复队列，不改变阶段一/二的异常全集、计数闭合和飞书证据文档。不得删除或修改历史 `TASK.md`。

## Process one item

### 1. Read evidence

用户选择处理后：

1. 置为 `处理中 + 代码准备`。
2. 读取窗口父文档和当前子文档 1–7 章；缺失、占位或关键链接不可用时阻塞。
3. 在 `TASK.md` 建立逐跳因果链，区分直接证据、同簇证据、代码推断和未证实。
4. 明确根因产生点、传播链、成功可排除节点、表面/二次异常及证据缺口。

### 2. Prepare code

按证据建立可迭代代码来源集合：入口应用必含；有 provider 异常、不完整 DTO、契约核对或二次异常责任的上下游按需纳入。

每个仓库：

1. 用 `$find-and-pull-hq-git` 搜索并展示候选；等用户确认项目、工作空间和布局。
2. 用 skill 脚本 clone/fetch，不手写 Git URL，不 pull。
3. 读取 `origin/HEAD`；无法确定默认分支时询问。
4. 计算标准基准名 `feature/exception-fix-baseline-{异常收集应用}-{MMDD}-{MMDD}`；日期不得带年份、小时或分钟。只检查分支是否存在，此阶段禁止创建基准。
5. 若本地基准已存在，必须由当前 `TASK.md` 证明它属于同一批次，并校验无 upstream、工作树干净和 HEAD；无法证明、命名不一致或状态异常时停止，不 reset、覆盖、重命名或另造变体。若不存在，记录“未创建”。
6. 选择任务起点：同批次基准存在时取其最新 HEAD，否则取最新远端默认 commit；同时记录起点 commit 和清理时的返回 ref。返回 ref 优先为同批次基准，其次为进入任务分支前的安全本地分支；两者都不可用时记录起点 commit，清理时允许回到 detached HEAD，禁止为返回而创建占位分支。
7. 从明确起点以 `--no-track` 创建 `feature/exception-fix-{ID}-{slug}`。已存在时只核验任务归属、起点、diff、commit 和 worktree 占用；不得删除、覆盖或把未知旧分支当作本任务继续。
8. 确认任务分支无 upstream，并逐仓记录起点、返回 ref、基准状态=`未创建/已存在`、任务分支和清理状态=`待判断`。

任何同步、来源、脏树或分支校验失败都进入阻塞；禁止 reset、stash、clean、rebase 或凭旧副本继续。全部仓库准备成功后进入分析。

### 3. Analyze and propose

跨仓确认真实责任点、传播链、表面异常和可观察行为。源码出现新应用的直接证据时，先登记候选，再走仓库确认与分支准备；弱猜测不得拉取。

#### Result-preservation gate

方案前必须完成以下审计：

1. 区分“必须消除的故障”与“应保持的原结果”。异常栈、错误噪音、超时和错误告警可以是待消除故障；调用方原本获得的业务数据、空值语义、降级结果和副作用不能因修复顺便改变。
2. 建立调用方矩阵。至少覆盖当前证据链直接调用方；若修改共享 provider、公共方法、DTO 或基础组件，搜索所有仓内可见调用方，并记录未纳入仓库或动态调用的证据边界。
3. 对每个调用方记录修改前基线：`success/errorCode/errorList/errorMsg`、`model/data`、null/空集合/默认值、响应结构、排序分页、缓存与数据源、下游调用次数、写操作/消息/任务等副作用，以及日志、指标和 trace 等可观测性。只记录与本项有关的维度。
4. 对跨服务或多调用方问题，至少比较根因产生点、服务/契约边界、调用方消费边界三类修复位置；不适用时说明原因。每个候选都写明能否消除故障、消费者语义差异、影响面、回归风险和验证难度。
5. 选择“消除已确认故障所需语义差异最小”的方案。允许修改层级或代码量略大，只要它更能保持既有消费者结果；禁止仅因某处一行可改就优先选择该处。
6. 对比前后结果。除已明确批准的故障消除外，默认保持调用方看到的业务数据、空值、成功/失败语义、错误码、结构、排序、缓存、下游调用和副作用。无法同时保持时，列出不可兼得项和受影响调用方，等待用户选择。
7. 日志或指标用于替代被消除的错误可观测性时，明确级别、关键定位字段和是否保留异常栈；不要为了结果保真而静默吞错。

“原结果”指故障发生前或调用方在该异常路径上已经依赖的消费者可观察契约，不等于机械保留 HTTP 500、异常栈或错误告警本身。证据不足以确定原契约时，不得自行猜测；把备选语义和证据缺口交给用户确认。

方案必须写入 `TASK.md` 并向用户说明：

- 现象、最终根因和置信度；
- 完整因果链、证据与影响；
- 调用方矩阵和原可观察结果基线；
- 候选修复层比较、选择的责任点及排除理由；
- 结果保真方案、必要语义变化及为何足够；
- 修改前后控制流和逐调用方可观察行为差异；
- 文件、测试、验证命令；
- 保持不变范围。

然后询问：`是否确认按上述结果保真方案修改代码？`

### 4. Implement and validate

确认后只修改批准范围；不顺手重构、格式化、增强日志、改配置或依赖。扩大范围或发现消费者语义与方案不一致时重新确认。运行定向测试及必要编译/检查，审计 diff 和用户已有改动，并把命令、结果、风险写入 `TASK.md`。

验证必须同时证明“故障消除”和“原结果保持”：为故障样本增加回归用例，并为每种受影响调用方语义增加契约断言。不能只断言不抛异常；应按方案断言 success/error、model/data、null/空值、结构、调用次数、副作用和 WARN/ERROR 可观测性中的相关维度。共享 provider 的异常路径改为成功空结果等行为时，必须验证错误列表为空、模型为空、正常路径不变，并审计全部可见调用方。

方案确认或实现验证明确某仓库只用于调用链分析、不承担最终修改时，应立即走“无改动分支清理”，不要把该任务分支留到批次末。

### 5. Commit and merge gate

验证通过后进入 `提交归并 + 待选择`，汇报每仓任务分支、实际改动、标准基准名、基准当前是否存在、验证和建议 message，询问是否提交并归并。此时没有实际改动的仓库不得创建基准。

确认后逐仓：

1. 核对任务分支与 diff；只暂存当前问题文件/hunk，不用 `git add .`。
2. `git diff --cached --check`，普通新 commit，不 amend/跳 hooks。
3. commit 成功且工作树干净后，再处理基准：同批次基准存在则切换复用；不存在则从该任务记录的起点 commit 执行 `git switch --no-track -c feature/exception-fix-baseline-{异常收集应用}-{MMDD}-{MMDD} <start-commit>`。不得用当前修复仓库名构造基准，也不得在名称中加入年份、小时或分钟。
4. 执行 `git merge --ff-only <task>`，校验任务 commit 是基准祖先、基准包含 commit、基准无 upstream、工作树干净。
5. 祖先和工作树校验通过后立即用 `git branch -d <task>` 安全删除本地任务分支，并校验分支已不存在；不得留到批次末，不得使用 `-D`。
6. 只有包含至少一个本批次实际修复 commit 且任务分支已清理的基准，才登记进入批次 push 清单。

非快进、冲突、脏树、偏离、hook 异常、分支被其他 worktree 占用或安全删除失败时停止并记录现场。用户处理后通知“已解决”或“放弃归并”；Agent 只复核。commit 已创建但归并或清理未完成时保留任务分支，不强删。

无新增代码但被既有提交完整覆盖时，记录 `已覆盖` 和验证即可，不创建重复 commit；仍须执行无改动分支清理，不得仅因覆盖结论创建基准。

#### No-change branch cleanup

当仓库仅用于分析、最终不在批准修改范围、实现后 diff 为空，或被既有提交完整覆盖时：

1. 核对任务分支工作树和 index 干净，且相对记录的起点没有需要保留的 task-only commit；若存在改动、未知 commit 或 worktree 占用，置为 `保留-阻塞`，不得删除。
2. 若同批次基准已存在则切回基准；否则切回准备阶段记录的安全本地返回分支；没有安全本地分支时 `git switch --detach <start-commit>`。不得因此创建基准或其他占位分支。
3. 用 `git branch -d <task>` 安全删除并校验不存在；不得使用 `-D`。
4. 记录实际改动=`无`、基准=`未创建`（或复用的既有基准未变化）、任务分支=`已删除`、push=`不纳入`。

“分析过该仓库”“读取调用链”或“创建过任务分支”都不算实际改动，不能触发基准创建。

### 6. Complete and advance

满足以下条件即可在本地标记 `已完成`：

- 代码准备 `已完成/不适用`；
- 根因、方案/无需新增代码结论和验证有证据；
- 提交归并为 `已归并/已覆盖/不适用`；
- 当前项创建的所有任务分支均已删除；若因未提交改动、未归并 commit、worktree 占用或校验失败而保留，则必须阻塞，不能完成；
- 仅有实际修复 commit 的仓库创建或复用基准并进入 push 清单，无改动仓库未因本项创建基准；
- `TASK.md` 已同步。

随后将下一未终态项设为唯一 `待处理`。不写飞书。

## Batch push

全部任务为 `已完成/已跳过` 后，只汇总 push 清单中的仓库：origin、标准基准名、HEAD、本批次 commits、工作树、任务分支清理结果和远端同名分支，并询问一次是否 push。确认后仅执行 `git push -u origin feature/exception-fix-baseline-{异常收集应用}-{MMDD}-{MMDD}`；任务分支永不 push。无实际修复 commit、未创建基准或任务分支未清理的仓库不得进入清单。失败时不强推、不改凭据。把结果只写 `TASK.md`。
